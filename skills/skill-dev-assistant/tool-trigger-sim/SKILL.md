## 1. 功能描述

对技能的 description 做**触发可行性分析**，含正负两向：**正向**——给定多种"用户会怎么说"的任务表述，逐句分析 description 的触发要素（职责动词、业务对象、输入输出词）是否覆盖，输出命中/存疑/不命中结论与改写建议，并生成供用户在 WorkBuddy 里实测的 3 说法话术模板；**负向**——与现有技能全量清单逐份比对语义重叠度，识别本技能会不会抢走其他技能的触发，输出冲突矩阵。**真机触发只能由用户实测，本技能输出的是推演结论，两者在报告中必须区分标注。**

**三种运行模式**（由用户意图判定，不明时问一次）：

| 模式 | 触发说法 | 输入 | 输出 |
|------|----------|------|------|
| 正向覆盖（默认） | "测测触发""这些说法能不能命中" | description + ≥3 种说法 | 命中推演 + 改写建议 + 实测话术 |
| 负向冲突 | "会不会抢别人触发""会不会和现有技能撞" | description + 现有技能清单 | 冲突矩阵 + 差异化改写建议 |
| 全量 | 同时要做两向 | 上述全部 | 推演 + 冲突矩阵 + 改写建议 + 实测话术 |

**边界**：

- 内：①多种任务说法的命中推演；②description 触发要素改写建议；③真机实测话术模板与结果记录表；④与现有技能的语义撞触发检测与分级。
- 外（不做）：①替代用户在 WorkBuddy 里实际触发（推演≠实测）；②SKILL.md 其他段落的规范检查（转 tool-skill-lint）；③知识库依赖实测（转 tool-kb-verify）；④判定冲突双方谁该让路（处置权在部门，本技能只给冲突事实与改写建议）。

## 2. 输入契约

**必需**（正向模式 / 全量模式）：

| 输入 | 说明 |
|------|------|
| 被检 description | 技能 frontmatter 的 description 全文（或整份 SKILL.md，自动提取） |
| 任务说法 ≥3 种 | 用户业务里典型的任务表述；用户给不出时按第 4 节规则生成后**请用户确认**再推演 |

**必需**（负向模式 / 全量模式）：

| 输入 | 说明 |
|------|------|
| 现有技能清单 | 调 list_skills 拉取 enabled 技能全量（slug / display_name / description）；工具不可用时请用户粘贴门户技能列表比对，**禁止凭印象罗列技能名** |

**可选**：技能 display_name（参与命中分析）；目标用户角色（业务人员/管理者，影响说法风格）；比对范围限定（如"只比同部门"）。

## 3. 输出契约

| 交付物 | 格式 | 命名 | 质量标准 |
|--------|------|------|----------|
| 触发推演报告 | Markdown（正式汇报版可导出 DOCX） | `trigger-{技能name}-{YYYYMMDD}.md` | 每种说法：结论（命中/存疑/不命中）+ 触发要素对照分析 + 建议 |
| 冲突矩阵（仅负向/全量模式） | Markdown（报告内嵌章节） | — | 逐技能给出重叠要素、危险级别、改写方向；附"AI 语义重叠度判断，非平台实际触发路由结果"标注 |
| description 改写建议 | Markdown（报告内嵌） | — | 改前 → 改后对照，改后仍须满足 ≤150 字三要素 |
| 真机实测话术模板 | Markdown（报告内嵌） | — | 3 种说法的完整测试话术 + 结果记录表（说法/是否命中/命中技能名/备注），供用户在 WorkBuddy 实测后填写 |

**正向结论标准**：**命中**（说法的核心动词与对象在 description 触发场景中有对应表述）/ **存疑**（部分对应，靠模型泛化可能命中）/ **不命中**（关键对象或任务类型无对应）。

**冲突分级标准**（负向模式）：

| 级别 | 判据 | 建议动作 |
|------|------|----------|
| **高危** | 核心职责动词 + 业务对象双重重叠（如两者都是"检查"+ "SKILL.md"） | 必须差异化改写，否则必有一个长期不触发 |
| **中危** | 业务对象重叠但职责动词不同（如都涉及"报告"，一个"编制"一个"核验"） | 建议各自加限定词区分适用场景 |
| **低危** | 仅泛化词重叠（"文档""材料""分析"等） | 可不改，记录备查 |

## 4. 工作流

1. **模式判定与要素提取**：按用户意图定模式（正向 / 负向 / 全量，不明时问一次）；从 description 拆出触发要素——职责动词（编制/检查/测算…）、业务对象（可研报告/技能/知识库…）、触发场景表述、输入输出关键词。
2. **说法准备**（正向/全量模式）：用户已给 ≥3 种说法 → 直接用；不足 → 生成补充说法（覆盖三种句式：祈使式"帮我编个可研"、名词式"出一份 XX 项目可研报告"、口语式"把这份材料做成可研"），**列出请用户确认**是否符合真实业务口吻（数据闸）。
3. **逐说法推演**（正向/全量模式）：对照触发要素表，输出命中/存疑/不命中与差距分析。
4. **冲突对撞**（负向/全量模式）：调 list_skills 取 enabled 技能全量 → 与每份 description 做要素重叠计算 → 按高危/中危/低危分级 → 出冲突矩阵。限定：只判语义重叠，不判平台实际路由结果；技能数 n>50 时降级为同部门优先比对，并在报告注明降级原因。
5. **改写建议**：不命中/存疑较多或存在高危冲突时，给出 description 改写对照（保持 ≤150 字、三要素齐全；冲突场景须体现"我与对方的区别在哪"，可提示同步检查 display_name 是否含关键业务词）。
6. **出实测模板**：生成 3 说法话术与记录表，明确告知"纸面推演通过 ≠ 真机命中，发布前必须在 WorkBuddy 实测并记录"。

## 5. 闸口

| 闸口 | 时机 | 动作 |
|------|------|------|
| 启动闸 | 推演前 | 确认模式与输入齐备：正向/全量需 description 原文 + ≥3 种说法；负向/全量需 description + 现有技能清单。说法不足先走生成+用户确认；清单缺失先调 list_skills，失败则请用户粘贴 |
| 数据闸 | 生成补充说法后 / 冲突结论写入报告前 | 补充说法须经用户确认贴近真实业务口吻再进入推演；冲突矩阵须标注"AI 语义重叠度判断，非平台实际触发路由结果，最终以真机实测为准" |
| 阶段闸 | 逐说法结论出来后 / 冲突矩阵出结果后 | 先给推演明细与冲突清单，用户确认要改 description 时再给改写对照 |
| 交付闸 | 报告输出前 | 每个说法均有结论与分析；冲突矩阵逐技能有级别与重叠要素；报告明确区分"推演结论"与"待真机实测" |
| 失败闸 | description 缺失/为空/与技能无关 / list_skills 不可用 | 停止推演，请用户补齐或改粘贴清单；禁止对空 description 假设内容，禁止凭印象罗列现有技能名 |

## 6. 知识库依赖

| 工作流步骤 | dept | 目录 | 查询意图（自然语言） | 未命中处理 |
|-----------|------|------|---------------------|-----------|
| 触发测试要求原文核对（3 种说法标准） | public | Platform/02-方法论库 | "智能体技能开发指南 触发测试 三种说法" | 换词重试（"智能体技能开发指南 SKILL.md 编写标准"）→ 按内嵌规则（三句式：祈使/名词/口语）执行并标注"规范库待核" |

> 注：负向冲突模式所需的 `list_skills` 属网关技能清单工具，**不属于知识库检索依赖**，故不在上表声明；其不可用时的降级方式见第 2 节与第 5 节失败闸。

> dept=`public` 指**公司公开库**（全员只读可见），公司级规范统一放此处，**不得引用任何部门私有库**——否则其他部门使用本技能时必然报「无权访问」。

## 7. 约束红线

1. 推演结论只声明为纸面分析，报告中不得出现"已通过真机测试"表述——真机结果只能来自用户回填；
2. 不命中结论必须给出具体差距（哪个要素缺失），不许只说"不命中"；
3. 改写建议不得突破 description ≤150 字与三要素约束；
4. 无密钥、无绝对路径；不修改任何技能与知识库内容，也**不主动提出代为应用改写**——只给"改前 → 改后"对照文本，是否采纳、如何落地由开发者决定；
5. 冲突检测**不判"谁该让路"**，只给重叠事实与差异化改写方向；改名、改描述、合并、下线等处置由部门决定；
6. 冲突结论必须基于 list_skills 实际返回的清单，不得凭印象补全或省略技能；清单缺失时如实标注"未核验"，禁止编造比对对象；
7. 高危冲突不得用"可能不影响"淡化，须明确表述"两者同时上架，长期将只有一个能被稳定触发"。
