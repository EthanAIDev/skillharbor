# 门户与技能网关集成回归

`scripts/test-skill-integration.cjs` 通过真实 HTTP 验证上传、网关预检、提交审核、管理员审批和最终发布。它启动当前门户代码与指定网关代码，不使用 mock inspect 响应，也不连接已经运行的服务。

## 运行

需要 Node.js 22 或更新版本，以及安装了网关依赖的 Python 环境。网关代码需包含 `/api/skills/inspect`、`/api/skills/prepare`、结构与组件接口，支持上传 `create_only` 并以 404 表示详情目标不存在；门户需包含 `/api/uploads/:id/prepare`。在门户仓库执行：

```powershell
node scripts/test-skill-integration.cjs --gateway C:\path\to\skill-gateway --python C:\path\to\venv\Scripts\python.exe
```

也可通过 `GATEWAY_REPO` 和 `GATEWAY_PYTHON` 环境变量指定这两个路径。脚本通常约需 15 秒；成功输出 `28` 个测试通过（27 个场景及外层测试），失败退出码为 `1`。不需要先启动门户或网关，也不需要真实账号或生产配置。

## 隔离方式

- 两个服务使用系统临时目录下新建的独立空数据目录，绑定随机 `127.0.0.1` 端口。
- 门户只配置三个虚构测试账号（管理员、上传人、另一上传人）；测试令牌固定为 `local-agent-test-only`。这些凭据仅存在于本次临时服务。
- 子进程不继承开发机的上游凭据。知识库、One API、IP 同步等地址指向 `127.0.0.1:1`；Docker 使用 mock，告警轮询关闭。
- 测试通过自身启动的接口写入合成技能包；不会上传到既有网关、生产快照或线上服务。
- 正常结束或断言失败时停止自身启动的子进程，校验临时目录范围后清理本次数据。

## 验证内容

1. Manifest 包的入口在 `main/SKILL.md`，包内技能和脚本在同级目录；预检不发布，审批后仍能读取两个组件全文。
2. 预检结构与发布后的对应版本结构完全一致，内部组件不作为独立技能出现在全局列表。
3. Manifest 更新采用声明版本，并保留旧版本组件内容。
4. Manifest 版本冲突不自增、不替换已有内容；检查最终版本及上传记录，不把审批接口返回成功等同于发布成功。
5. 旧单 Markdown 可以发布；更新时即使 frontmatter 改名，仍使用绑定 slug。
6. 已有 `v3.4.9` 的旧技能自动更新为 `v3.4.10`。
7. 歧义根目录保存为有候选入口的草稿，报告为失败，未应用清单不能提交；缺少必要依赖的包也不能提交审核。两类草稿均不写入技能注册表。
8. 长 manifest 版本号不被截断；manifest 身份与更新目标不一致时在提交阶段拒绝。
9. 网关接受的带 UTF-8 BOM Markdown 同样能通过门户解析和发布。
10. Python 标准库独立生成的压缩包（不足 1 MB、解压后超过 51 MB）经过门户重新打包发布后，中文路径及文件 SHA-256 保持一致，验证 DEFLATE 和 CRC 的跨服务兼容性。
11. 管理员预检代理保留网关结构响应；声明 `Content-Length: 156 MiB` 的请求在接收正文前返回 HTTP 413。
12. 未设置 ZIP UTF-8 文件名标志、使用 GBK 中文目录与文件名的旧包，可以完成门户解析、提交和审批发布；预览与发布结构一致，组件可通过 HTTP 读取，包含二进制资产在内的全部文件字节保持一致。
13. 无 manifest、入口在 `main/SKILL.md` 且脚本或资产位于其目录外的包，分别覆盖有、无 wrapper 目录；保留所有原文件并生成不可提交草稿，候选清单采用覆盖兄弟文件的外层根，未应用不发布。
14. 路径穿越、大小写冲突路径、CRC 损坏等不安全 ZIP 仍解析失败，不创建草稿、不遗留暂存文件、不写入注册表。
15. 两个兄弟入口的歧义包完成选择入口、编辑组件与步骤、预览、应用、提交、审批和发布。预览逐项比对原文件 SHA-256、持久化上传记录和注册表文件，确认零写入；应用只新增一个清单，发布后兄弟入口、脚本、文本和二进制 SHA-256 全部保持一致。重复应用旧 revision 被 HTTP 409 拦截。
16. 未选择有效入口、非法路径、缺失组件、未声明的步骤 target、入口与清单不一致、缺少或过期 revision，均不能应用；另一用户及管理员不能编辑上传人的草稿，已提交草稿不能再修改。拒绝操作后文件、记录和注册表完全不变。
17. 必需依赖不存在时可以应用并保存清单，但报告仍失败且不能提交；创建合成依赖后，旧错误 slug 仍不自动匹配。编辑成准确 slug 后重新预览、应用、发布，预览成功本身不会清除旧失败报告。
18. GBK 中文文件名 ZIP 的无效 `AGENT.YAML` 可经选择中文入口修正；应用保留原有清单文件名大小写，所有其他文件及二进制资产的 SHA-256 在草稿和发布版本中一致。
19. 绑定更新先检查所有权和稳定身份：不存在或他人所有的 slug、工具通道绑定、清单 id 与更新对象不同均拒绝。应用后提交省略 `updateOf` 会继承已确认绑定，显式清空或换目标返回 409；合法发布保留旧 slug 并产生新版本，不因入口 frontmatter 改名而创建资源。
20. 管理员驳回技能后仍保留源文件，上传人可以恢复草稿、预览和应用清单、重新提交并发布。
21. 普通 HTML 工具继续正常解析、提交和审批发布，并能通过 HTTP 读到原始 HTML；工具不能调用技能 prepare，发布也不产生技能注册表记录。
22. YAML 语法正确但 schema 不合法的清单，仅选择入口不会自动覆盖原清单；显式 `regenerate: true` 后生成合法清单，保留原稳定 id 和版本，提示核对手工关系，应用后可完成发布。
23. 依赖问题与引用方代理接口仅管理员可读，匿名和普通上传人均返回 403；管理员能读取准确依赖引用结果，读取前后上传记录与技能注册表文件完全一致。
24. 已确认更新的草稿可以改成新建，但需要显式空 `updateOf`、新的唯一清单 id，并重新预览和应用；预览不清除旧绑定，应用成功后才解绑，发布不会改变原目标的元数据或文件。
25. 新建包的清单 id 指向他人或本人已有 slug 时，即使版本号和显示名均不同，未绑定更新也不能提交。直接解析和预览应用后的草稿均受保护；拒绝后上传记录、注册表、旧版本及文件 SHA-256 不变。
26. 两个同 slug、不同版本和显示名的草稿可以在目标尚未存在时进入审核；首个审批发布后，后一个审批必须拒绝追加版本，不得改变获胜资源的元数据与原文件。
27. 同时向真实网关发起两个同 slug、不同版本的 `create_only=true` 上传，只能有一个成功；最终目录仅包含获胜版本，当前版本和入口内容一致。

## 草稿接口断言

`POST /api/uploads/:id/prepare` 预览请求可携带 `entry`、结构化 `manifest`、`updateOf: "skill:<slug>"`；响应包含 `assistance`，初始 `revision` 为 `0`。预览不持久化清单或更新报告，重新读取草稿应保持原状态。

省略 `updateOf` 继承已确认绑定，显式空字符串表示准备改为新建；只有应用成功才持久化解绑。提交接口不允许直接清空或更换已应用的更新绑定。

无效原清单需要重建时，预览可显式携带 `regenerate: true` 和已选 `entry`，不同时传 `manifest`；核对返回的新清单后按普通应用请求提交。

应用请求携带已确认的 `manifest`、`apply: true` 和预览返回的 `revision`。成功后 `revision` 加一，并返回重新预检的 `report`；安全结构或清单错误不落盘，外部必需依赖缺失则允许保存为失败草稿。测试读取自己启动的临时服务数据目录，验证实际文件与持久化记录，再检查审批后的网关版本，不能仅凭 HTTP 200 判断应用或发布成功。

这些是本地后端集成断言，不包含浏览器渲染、真实外部知识库或线上部署验收。
